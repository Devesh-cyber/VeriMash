THE PROBLEM

How can Chain B trust an event on Chain A?

Two separate blockchains do not automatically know what happened on the other. In VeriMash v2, three independent validators each read Chain A themselves and vote directly on Chain B. The destination contract counts the votes and accepts the message only when 2 of 3 agree on the exact same content.

What v2 proves

A user signs a real transaction on Chain A from their own wallet. Three validators, each with its own key and RPC provider, independently confirm the event after block confirmations and vote on Chain B. No server carries the message: the destination contract itself enforces the 2-of-3 threshold and rejects forgery, tampering and replay.

What it does not claim

Validators are honest-majority: two colluding validators could approve a false message. The validator set is fixed at deployment. Next steps are staking with slashing and on-chain receipt proofs. This is a message-verification prototype on test networks, not a transfer of real cryptocurrency.

Security Lab

Ask the live destination contract how it treats replay, outsiders, a lone validator and tampered messages.

SECURITY VALIDATION

Security verification tests

Each test is a read-only call to the deployed gate contract on Chain B, simulating the attack. Nothing is written and no gas is spent.

DEMO TESTS
Replay protection

A validator re-submitting an already delivered message should fail.

Outsider rejection

A relayer, hacker or server that is not a validator should be rejected.

Validator threshold

One validator alone must not be able to deliver a forged message.

Source evidence integrity

An altered message must not match the source event or be accepted.

Tests use eth_call against the real deployed contract, so the revert reasons are exactly what the chain returns. To run the attacks as real on-chain transactions, use npm run attack.
